## 方法

硬件为 AMD Ryzen 9 9950X3D2，32 个逻辑 CPU；保留 CPU 0–31 的默认 affinity，保留生产最多 8 个模板线程。两版都用 rustc 1.97.1、LLVM 22.1.6、default-feature release、`--locked`、debug symbols 1、关闭 incremental。诊断版另启用 profiling feature。编译与本会话的计时工作不并行，整机其它负载与 CPU 频率不锁定，保留慢样本。

- **CLI 主样本：** 每版一次 warmup，再各六个新进程，逐轮 AB/BA 交替。正式样本已有相同磁盘输出，publish 仍实际读取比较全部输出，不是无条件跳过。进程 wall 从 Popen 前到 wait4 返回，包含扩展、组装、发布、析构和退出。
- **阶段诊断：** 当前源码 coarse / detail 各一次 warmup、三次正式样本，独立二进制；不与正常秒数混算。没有显式移动任何 SSG 对象的销毁边界，保留当前 consume-during-HTML 生命周期及自动 Drop 顺序。
- **真实 serve：** before/current/current/before 四个独立普通进程，每个初次构建后同字节写回首页触发三次重建；每版两次初始、六次重建。记录生产终端的 Updated 毫秒，不用 CLI wall 代替。这里验证报告的完整页数，不声称逐修订核对全部 HTTP 字节或覆盖九种编辑语义。
- **RSS：** 另跑 AB/BA 四个普通进程，20ms Rust-only `/proc` RSS 采样。内核 wait4 高水位也记录；它是进程及已等待子进程的保守最大值，不是各进程相加。
- **其它：** 当前版独立 strace、Python cProfile、消费者全量静态链接检查。编译、指纹核对、这些独立观察器均不混入普通计时。
- **分配流量补充：** Linux/glibc 下独立拦截 malloc/calloc/realloc/free，两版各两次 AB/BA，原样转发到 glibc，仅对准确匹配的 Rust executable 计数，Python 子进程不计入。对齐分配 API 和 libc 内部调用不完整；requested bytes 是重复分配流量，不是存活堆、峰值或泄漏证据。该观察器的时间不作加速数据。

Updated 仍只覆盖 target 组装，不含磁盘发布、watcher debounce、旧站点替换、HTTP 传输或浏览器渲染。因此与 CLI 的绝对秒数不能直接等同。

## 源码变化的解释边界

相对原始 `85ab69e`，当前生产包括共享/COW 身份与来源文本、来源链、求值局部实例查找缓存、PresentCheckpoint、小字典索引/容量优化，以及 HTML 阶段消费已渲染 Document 等修改。当前 profile 只测它们合在一起的表现，不把每项历史实验收益相加，也不从总差值反推每一项独立贡献。

尤其要注意：现在 `documents.into_iter().zip(handles)` 在正文渲染循环中消费并释放树。正文阶段包含了原先一部分函数返回时的销毁工作；若它占比提高，不代表 HTML renderer 单独变慢。诊断分别记录 renderer、registry 子项与整个正文循环，但未命名 Self 仍可能包含链接、局部析构、分配器工作和计时开销。

密集探针记录的是嵌套 inclusive/Self **wall time**，不是 perf sampled CPU Self。递归 present / bind_content 的 inclusive 可超过进程 wall，不能相加。模板范围由主线程包围 worker joins，不把多线程 CPU 秒误加进 wall 分区。

## 内存与分配流量

### 同口径 Rust RSS

两个独立诊断进程的 Rust VmRSS 峰值（KiB）：

- 旧版：`6,853,364 / 6,853,436`。
- 当前：`3,501,252 / 3,501,352`。

各取最大观测值，同口径从 **7,017,918,464 → 3,585,384,448 字节**，即 **6.536 → 3.339 GiB，下降 48.91%**。这是 20ms 采样，可能漏掉极短峰值；只采 Rust 进程，不含 Python 子进程，也没有测 serve 同时保留旧/新两版站点时的峰值。

wait4 内核高水位也全部保留，但其进程/子进程范围和 RSS 记账口径与 `/proc` 采样不完全相同，不把二者混成同一序列计算下降。没有把 Python 启动器的历史高水位当作 Rust 排名，也没有把多个进程的最大 RSS 相加。

当前仍有约 3.34 GiB 工作集，不能说“内存问题已解决”。完整拥有的输出字节本身就是 **451.8 MB**；若后续目标是 300,000,000 字节的 live memory，则必须讨论输出/树驻留策略，不能仅靠更小的 Dict 就宣称达到。live allocation 与 RSS 不是同一个指标，本轮没有做精确存活堆归因。

### 观察到的分配 API 流量

独立 glibc API 观察器，两次均值；realloc 成功也包含在“分配/重分配”总次数里，不重复相加：

| 指标 | 旧版 | 当前 | 下降 |
| --- | ---: | ---: | ---: |
| 成功分配/重分配次数 | 327,078,361.5 | 198,475,261.5 | **39.32%** |
| requested bytes | 24,295,855,009 | 15,050,053,062 | **38.06%** |
| 非空 free 调用 | 304,643,767.5 | 184,828,346.5 | 39.33% |
| realloc 次数（上面总数的子集） | 22,432,926 | 13,645,247 | 39.17% |

这支持“共享/紧凑容器确实减少了大量分配流量”，不只是把释放挪到更晚。仍有近 **2 亿次 API 分配事件 / 15 GB requested 流量**，与数百万通用求值调用一起，是当前值得进一步做堆/CPU 栈采样的方向。

但不能把 15GB 当成存活内存：重复临时分配会累加，realloc 按完整新请求长度计数，且对齐入口和 libc 内部调用不完整。分配数/free 数不守恒也不能推导泄漏。拦截会明显改变运行时间，因此 `alloc-*.json` 的 wall 从不参与加速/RSS 成绩。该观察器没有分配栈，不把全部流量归罪到某一个函数或某一类节点。

## 下一步调查优先级（本轮不实施）

1. **求值器小操作与分配。** 当前约 4.05s 的 coarse 求值范围最稳定，数百万 execute/present/bind 仍在；下一步先用 CPU/分配栈把通用参数、字典、临时身份、捕获/内容缓冲区细分。密集探针的 Self 不能替代真实采样，不能再把已经实现的实例缓存当新方案。
2. **正文循环中的树生命周期和内存表示。** 现在它同时承担 HTML、链接和逐页释放，应区分 renderer 与百万级节点/容器释放；在不删权威树、字段、来源、预算和语义的前提下研究实际存活工作集。不要用“挪到 Updated 后”制造加速。
3. **静态资产及安全 IO 的可复用部分。** 约 333.7 MB 的静态输入和全量文件比较仍在；共享不可变资产需要可靠失效/授权机制，不能仅信 mtime。publish 优化只改善 CLI，不能直接解释 Updated。
4. 暂不优先 JSON parser、模块编译、Python 编码和 Tera。也不因本轮观察而重新尝试上一活动已拒绝的候选或开启第十一轮优化；那需要新的实现授权和独立验收。

本轮所有性能下降百分比只对应明确列出的相同口径样本；不是对每种消费者/编辑负载的普遍保证。

- `rss.json` / `logs/rss-*.rss.json`、`strace-current.txt`、`python.pstats`、`semantic-check.stdout` 保存独立诊断。
