# icexiv-db：Item／闭包执行内核重构后的整站 profile

## 结论

这次重构在表示与执行模型上成功，但不能把合成测试收益说成真实站点的大幅提速。
同一份当前 consumer 输入下，`e07b67e` → `c722ecb`：

- 干净 release 整站中位数 **9.4738 → 9.4344 s（−0.42%）**。三组交错样本不足以证明有意义的整站加速。
- 峰值 RSS **3,518,504 → 3,372,884 KiB**，减少 **142.21 MiB／4.14%**。
- 分配 API 事件 **1.9837 亿 → 1.9596 亿（−1.21%）**；累计请求字节 **15.125 → 14.015 GB（−7.34%）**。
- 两版及全部成功探针构建的 **78,004 个产物逐字节相同**；全部物品、目录与本地 HTML 链接校验通过。

当前时间主要花在 **求值、链接／HTML／树销毁、前端分析及资产处理**，不是模块反复编译、JSON 反复解析或 Tera。

## 2. 整站时间去向

下表为两个 coarse 样本的均值；以 CLI 内部总区间 9.4078 s 为分母。
它略小于进程外部 wall（中位数 9.4955 s），后者还包含启动、退出等边界。
coarse 对初始干净重复样本中位数的观察开销约 0.2%。

| 阶段 | 秒 | CLI 区间占比 |
|---|---:|---:|
| 求值 | 3.9199 | 41.67% |
| 正文处理：链接、HTML、树释放等 | 2.2396 | 23.81% |
| 前端分析／检查 | 0.9492 | 10.09% |
| 资产处理 | 0.7825 | 8.32% |
| 发布 | 0.4611 | 4.90% |
| Python 扩展 | 0.3000 | 3.19% |
| 其他：上下文、准备、析构、宿主等 | 0.7555 | 8.03% |

完整互斥分区在 `summary.json` 的 `coarse_partition`，不是递归 inclusive 时间相加。
共享站点上下文约 0.1436 s，Tera 阶段约 0.0678 s（0.72%），都不是首要瓶颈。
发布时间主要是已有产物比较；这不是首次写出所有文件的成本。

| 正文工作 | 秒 |
|---|---:|

| 结果树自然销毁 | 0.3939 |

销毁探针在字段的自然析构位置测量，没有提前释放树来制造更好的时间或 RSS。
这些数字来自另一组探针，不能强行与 coarse 的 2.2396 s 拼成同一次测量。

## 3. 求值内部实际做了什么

coarse 中物品页求值累计 3.2539 s，约 **63.5 µs／页**；目录页累计 0.6535 s，约 **1.27 ms／页**。
目录页仅约 1% 的页数，却消耗约 16.7% 的求值时间：每页包含约 100 项列表循环。

detail 探针确认：

- `execute` 与 implementation 查询各 **6,073,286 次**。
- `present` **8,440,426 次**。
- 内容绑定 **2,213,972 次**。
- data native **1,955,784 次**。
- 51,738 次数据读取中，实际 parse **565 次**，parse hit **51,173 次**。
- 模块实际编译工作 **1 次**，实际 binding 工作 **3 次**。

detail 观察开销约 **23.7%**，用于计数和定位，不能当真实整站时长。
例如递归 `present` 的 inclusive 累计约 50.68 s，超过进程约 11.72 s，完全正常；不能据此说它独占 50 秒。

当前 `modules/views.notc` 中，物品页是一个较宽的 Code view，内含许多数据读取、投影、普通 native 调用与内容构造。
它不是合成测试里反复调用许多小 Code 函数的结构。去掉捕获代换和 checkpoint 的收益不会按 synthetic 比例映射到这一工作负载。

## 4. CPU 栈与源码证据

系统拒绝 `perf record`，未更改系统权限。替代为 gperftools **libprofiler + libunwind** 的 199 Hz CPU 采样，未加载 tcmalloc。
preload 按可执行文件身份启用，Python 子进程不启动采样，不会覆盖 profile。
两次采样构建 wall 为 9.449／9.485 s，采到约 9.382／9.437 CPU s；CPU 百分比不是整站 wall 百分比，且不含 Python 扩展 CPU。

两次稳定出现的热点：

- `_int_malloc` flat 约 10–11%；其它 malloc/free 路径同样明显。
- `Arc::drop` flat 约 5–7%，`Arc::clone` 约 3–3.5%。
- `memcmp` flat 约 4–6%，`memmove` 约 3–4%。
- 路径组件比较 `std::path::compare_components` 第一次 cumulative 约 **9%**。

这些反映对象生命周期、共享引用计数和键比较的成本，不能全都归为词法 Scope。
源码采样中 `Scope::insert` cumulative 约 **95 ms／1%**，不足以支持“先把所有作用域改槽位”是首要整站优化。

`execute-lines.txt` 中，参数求值约 759 ms cumulative、字段插入约 296 ms、实现查询约 367 ms。
它们是有内联、递归和采样误差的源码归因，不是互斥阶段，不应加总；可用于选择实验，不用于承诺收益。
分配、Arc 与路径比较也需要沿调用栈归属，不能把 allocator 百分比直接当成可完全消除的开销。

## 5. 重构前后究竟变化在哪里

相同输入、相同 clean 发布条件、交错顺序：

| 配对 | 重构前 s | 新内核 s |
|---|---:|---:|
| 1：前→新 | 9.4671 | 9.4161 |
| 2：新→前 | 9.5169 | 9.4812 |
| 3：前→新 | 9.4738 | 9.4344 |

三次均略快，但仅约 36–51 ms；没有足够样本、隔离或置信区间支持“大幅提速”。
另两组同 coarse 探针的阶段 A/B：

| 阶段 | 重构前 s | 新内核 s | 变化 |
|---|---:|---:|---:|
| 全部求值 | 3.9861 | 3.8697 | −2.9% |
| 物品页求值 | 3.3579 | 3.2094 | −4.4% |
| 目录页求值 | 0.6162 | 0.6486 | +5.3% |
| 正文阶段 | 2.2443 | 2.2423 | −0.1% |

这说明局部收益不均匀；目录页回退值得独立研究，但两组探针还不足以确定机制。
coarse A/B 不能替代 clean A/B；其总区间差异约 1.4%，也不能宣传成 release 整站收益。

分配诊断每版两次，结果几乎完全一致：

| 指标 | 重构前 | 新内核 | 变化 |
|---|---:|---:|---:|
| 成功分配 API 事件 | 198,372,804 | 195,962,918 | −1.21% |
| 累计请求字节（十进制 GB） | 15.125 | 14.015 | −7.34% |
| realloc 事件 | 13,542,789 | 14,468,435 | +6.83% |

realloc 已计入分配事件；累计请求量包括其请求大小，不是净分配、更不是峰值堆。
此探针只观察 glibc malloc/calloc/realloc/free API，排除 aligned 入口与 libc 内部调用；不替换分配器，不用诊断运行时长作性能结论。
**每次请求的字节总量减少了，但高频短命分配并没有消失**，与 CPU 采样相符。

RSS 仍约 3.22 GiB，不能靠本次诊断断言全是求值器；当前 SSG 的全站分析／结果驻留与公共宿主缓存仍是独立研究方向。
语言执行效率、公共宿主基础设施、站点生命周期策略，应继续分开定义与验收。

## 6. 下一轮实验优先级（本轮没有实施优化）

1. **普通 native 调用与内容构造的临时分配**：沿 `execute` 参数、fields、implementation 与返回内容路径归因；同时测物品与目录 workload，关注 realloc 增长。保留预算、身份、来源、错误恢复与重复挂载语义。
2. **不可变元信息与身份复用**：对函数实例、来源、键与共享对象 clone/drop 做精确 attribution，验证减少临时分配和 Arc 操作是否有 clean 整站收益；不能仅根据 flat allocator 热点就改 allocator。
3. **链接／路径遍历及查找**：正文约 0.75 s 链接工作，另有跨阶段路径比较热点。研究重复规范化、路径键和重复遍历；保持授权、资源版本与跨页校验契约。
4. **独立内存工作包**：研究 SSG 分析和页面树的生命周期、跨页信息投影与产物存储，不把它混作语言执行内核的槽位优化。

不优先：模块缓存再重写、JSON parser 替换、Tera 替换、无证据的全面 Scope 槽位化。
每个实验应重新交错 clean A/B、完整产物对照和 consumer 语义校验；局部 microbenchmark 仅作为辅助。
