1. **完整 XIV 的成本分散在发布、生成准备和文档分析**，分别占阶段探针内总耗时约 24.1%、22.7%、18.8%；逐页模板占 13.2%。只优化模块编译或 HTML Renderer 无法解决它的大头。

6. 五个主负载均没有语言 Data API 调用；SSG 的 site.data 序列化约 95 ms 是另一个宿主阶段。JSON／TOML 正向控制确认读取、解析与命中探针都连通。

宽导出发生 105,031 次 execute、178,336 次所选 Item clone、88,647 次 prototype clone 与 88,647 次 children clone。这里是**显式 clone 调用次数，不是底层被复制节点数**；一次 Item clone 可以继续递归复制子树。结构校验 89,168 次仍仅约 4.46 ms，次数多不等于主要耗时。

代码与测量相互对应：

- `crates/notist-core/src/item.rs:382`：Item 的派生 Clone 会复制 children Vec，以及 pending／origin 等拥有的数据。
- `crates/notist-pipeline/src/code/eval.rs:420`、`:431`：bind_content 先 node.clone，再递归重建 children，旧的整棵 children 拷贝随后被替换。
- 同文件 `:496`–`:498`：present_node 同样先 clone Item，再递归呈现 children。
- 同文件 `:598`–`:602`：present_call 分别克隆 children 与完整 prototype；execute 随后又重设 prototype 的 fields、pending、target、evaluation 和 children。
- 同文件 `:1023`：每次实现查询返回 definition/body 的拥有副本；模块编译命中 comemo 不会自动消除这里的 checked body clone。

因此下一步应先审查 Item／内容调用的所有权流和可共享的不可变定义，减少“先整树复制、后覆盖 children／pending”的工作，同时保持 Analysis 不可变、扩展映射、错误边界和展开来源。不能根据本表直接跳过求值、删除结构／预算检查，或用缓存命中代替真实模块工作。
